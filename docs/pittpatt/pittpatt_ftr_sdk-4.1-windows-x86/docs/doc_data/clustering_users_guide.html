1. Definitions and Terminology

Clustering

Clustering is the process of automatically grouping subjects such that all instances of the same subject are in the same group. For example, consider a set of images where subject A, subject B, and subject C appear multiple times. Clustering can be used to group the images such that all images of subject A are in a group, all images of subject B are in a different group, and all images of subject C are in a third group.

2. Introductory Topics

Clustering Aggressiveness

A clustering aggressiveness between 0 and 10 can be specified when generating a subject list from a gallery. An aggressiveness of 0 will do no clustering, and the generated subject list will simply be a representation of the information the user has provided about template relationships. In this case, any templates that do not have a specified relationship to any other templates will be their own subject. If the clustering aggressiveness is 0 and no template relationships have been assigned, then each template will be its own subject.

When the clustering aggressiveness is greater than 0, clustering is performed to determine which templates belong to the same subject, taking into account the user-specified template relationships.

Higher clustering aggressiveness results in less subjects with more templates in each subject. Lower clustering aggressiveness results in more subjects with less templates in each subject. The trade-off is that very aggressive clustering may group templates even though they are not the same subject, while less aggressive clustering may assign templates to different subjects even though they are the same subject. Regardless of the clustering aggressiveness, the user-specified template relationships will not be violated. If all template pairs have been assigned a relationship, then the generated subject list will simply be a representation of information the user has provided, and will be the same regardless of the clustering aggressiveness.

Multi-Gallery Clustering

Clustering a gallery into subjects requires comparing every template in the gallery to every other template in the gallery. This means there is a squared dependence between the number of templates in the gallery and the number of comparisons that must be performed to do clustering. Therefore, as galleries become larger, the number of required comparisons grows quickly. As many templates are added, it becomes unfeasible to compare every template to every other template in a reasonable amount of time.

Multi-gallery clustering addresses this issue by using a two-stage clustering approach that greatly reduces the number of comparisons that must be performed. Instead of creating one large gallery, the user creates several smaller galleries, which form a gallery group. Each gallery in the gallery group is clustered independently. From each resulting subject, a number of templates are strategically selected to represent that subject in stage two. Stage two clusters the representative templates. Subjects from the stage one galleries are merged based on how their representative templates were clustered in stage two, producing a final clustering result.

The clusters that result from multi-gallery clustering are typically less accurate than clustering results obtained from clustering one large gallery. However, for applications where time and/or memory is limited, multi-gallery clustering may be the only option. The accuracy penalty can be mitigated by intelligently deciding how the entire set of templates is split into smaller galleries. If there is a high probability that a set of templates has many of the same subjects, it is best to place those templates into the same gallery. For example, a photo management application may choose to divide templates into galleries based on events where the photographs were taken. Because the probability that there are photos of the same person within an event is higher than the probability that there are photos of the same person across events, it makes sense to create a separate gallery for each event.

When dividing templates into galleries, it is also important to avoid galleries with too few or too many templates. If galleries are too small, there may be little clustering in stage one, making the two-stage approach less useful. If galleries are too large, the original problem of doing too many comparisons still exists. For the photo management application example above, this may mean putting multiple events into a single gallery, or breaking a single event into multiple galleries.

Gallery Groups

A gallery group is a collection of galleries for multi-gallery clustering. Each gallery is assigned an ID as it is added to a gallery group. Gallery IDs are unique within a given gallery group but not across galleries groups. Gallery IDs are assigned incrementally, starting at 0 and are not reused within a gallery group (i.e., if a gallery is removed from a gallery group its ID will never be assigned to another gallery that is added later).

Because galleries are so large, a gallery is not copied when it is added to a gallery group. Instead it is moved. The gallery group takes control of the gallery, and the user can gain access to the gallery by requesting a reference to it. Any changes made to the referenced gallery affect the gallery in the gallery group. The user must release the reference when it is no longer needed. Operations such as clustering cannot be performed on a gallery group if there are outstanding references to galleries within that group. A gallery may only be added to one gallery group.

A gallery group also maintains user-specified relationships between templates within the same gallery and between templates in different galleries in the group.

Template Sources

An individual template inside of a gallery group cannot be specified using the template ID alone. Since template IDs are unique within, but not across galleries, specifying a template in a gallery group requires not only the template ID, but also the ID of the gallery that contains it. The term 'Template Source' is used to encompass a template ID and its gallery's ID.

Back to top.

Inter-Gallery Subject Lists

An inter-gallery subject list is the result of multi-gallery clustering. This is different from a regular subject list because the subjects are a list of template sources rather than a list of template IDs. For multi-gallery clustering the resulting subjects must be in the form of template sources because they are generated from a gallery group, and therefore require not only a template ID, but also a gallery ID to fully specify a template.

3. Advanced Topics

Representative Templates

Multi-gallery clustering is able to perform fewer comparisons than full clustering because only a select few templates from each stage one subject are passed along to stage two. The templates selected from each subject are called representative templates. The number of representative templates taken from each stage one subject can be specified using ppr_set_num_representative_templates_per_subject.

Using fewer representative templates per stage one subject reduces the number of comparisons required in stage two because fewer templates are passed to the second stage. However, using a greater number of representative templates increases accuracy because the stage one subjects are better represented in stage two. This speed vs. accuracy trade-off must be considered when selecting the number of representative templates to use. Setting the number of representative templates too high will pass so many templates to stage two that it could defeat the purpose of using multi-gallery clustering.

Back to top.

Stragglers

Subjects that have few templates in stage one are called stragglers. Depending on the application, such subjects may be unimportant, and therefore it may not be necessary to pass them along to stage two. If so, the number of stage two comparisons can be reduced by not representing the stragglers in the second stage.

The number of templates required for a subject to not be labeled a straggler can be set by calling ppr_set_straggler_cutoff. If the number of templates in a stage one subject is less than or equal to the straggler cutoff, that subject is considered a straggler. Therefore, if the straggler cutoff is set to 0 then no stage one subjects will be labeled as stragglers, and all subjects will be represented in stage two.

Disk Gallery Groups

A gallery group can become very large since it may contain many galleries, each of which may contain many templates. Depending on the size of the gallery group and the amount of memory in the system, the gallery group may be too large to fit into memory. A disk gallery group stores galleries on disk and only loads a gallery when it is needed. During multi-gallery clustering, only one gallery is needed at a time. Any gallery that has an unreleased reference must also be in memory, so to reduce memory requirements, outstanding references to multiple galleries should be avoided.

When a gallery group is created, read from disk, or unflattened, a scratch directory can be specified to provide a place for galleries to be stored on disk. The scratch directory must already exist - it is not created by the SDK.

Using a disk gallery group comes with a penalty because time must be spent performing disk I/O. However, when clustering large gallery groups, the disk I/O time is often insignificant compared to the time taken to perform clustering.

4. Clustering Framework

Frameworks for using the clustering portion of the FTR-SDK are described below. The frameworks provide an introduction to the order in which functions should be called, with links to each function's detailed description.

Single-Gallery Clustering

  1. Get a new context

    Call ppr_get_context to get a new context with the default parameters. The returned context should be stored for submission to future function calls.

  2. Enable recognition

    Recognition must be enabled in the context before initialization since recognition functions will be used. Call ppr_enable_recognition to allow recognition functions to be used in the context.

  3. Configure the context

    Certain parameters cannot be configured after the context is initialized. Therefore, unless the default values are desired, the parameters must be configured before the initialization step. The function references indicate which parameters must be set before initialization.

  4. Initialize the context

    After configuring the context, ppr_initialize_context must be called before the context can be used.

  5. Get a gallery

    Follow the steps in the Creating Galleries section to create a gallery. Alternatively, a previously saved gallery can be read from disk by calling ppr_read_gallery.

  6. Cluster templates in the gallery

    The ppr_cluster_gallery function clusters templates within a gallery to create a subject list. The resulting subject list indicates which templates belong to the same subject.

  7. Free allocated memory

    Any galleries that were created or read from disk must be freed using ppr_free_gallery when they are no longer needed. Subject lists must be freed using ppr_free_subject_list.

  8. Release the context

    Call ppr_release_context to inform the SDK that the previously allocated context is no longer required. Each context must be released to avoid memory leaks.

  9. Finalize the SDK

    Call ppr_finalize_sdk to inform the SDK that it is no longer needed. This function releases the SDK's internally managed memory buffers. It must be called before exiting the program.

Creating Gallery Groups

  1. Get a new context

    Call ppr_get_context to get a new context with the default parameters. The returned context should be stored for submission to future function calls.

  2. Enable recognition

    Recognition must be enabled in the context before initialization since recognition functions will be used. Call ppr_enable_recognition to allow recognition functions to be used in the context.

  3. Configure the context

    Certain parameters cannot be configured after the context is initialized. Therefore, unless the default values are desired, the parameters must be configured before the initialization step. The function references indicate which parameters must be set before initialization.

  4. Initialize the context

    After configuring the context, ppr_initialize_context must be called before the context can be used.

  5. Create a gallery group

    Galleries groups can be created using the ppr_create_gallery_group function. The newly created gallery group is empty (i.e., it contains no galleries).

    Alternatively, a previously saved gallery group can be read from disk using ppr_read_gallery_group.

  6. Get galleries

    Follow the steps in the Creating Galleries section to create galleries. Alternatively, previously saved galleries can be read from disk by calling ppr_read_gallery.

  7. Move galleries to the gallery group

    A gallery can be moved to a gallery group using the ppr_move_gallery_to_gallery_group function. The gallery group is given a pointer to the gallery, and the gallery is assigned an ID. The user's reference to the gallery is no longer valid.

  8. Specify template relationships

    If two templates are known to be the same subject or different subjects, this can be specified using ppr_set_template_source_relationship. This function can be used regardless of whether the templates are in the same gallery or are in different galleries.

  9. Process the gallery group

    A gallery group can be clustered using Multi-Gallery Clustering to produce subject groupings. The gallery group can be saved to disk by calling ppr_write_gallery_group.

  10. Free allocated memory

    Any gallery groups that were created or read from disk must be freed using ppr_free_gallery_group. Inter-gallery subject lists must be freed using ppr_free_inter_gallery_subject_list. Galleries that were moved to the gallery group are freed when the gallery group is freed, and therefore should not be freed by the user.

  11. Release the context

    Call ppr_release_context to inform the SDK that a previously allocated context is no longer required. Each context must be released to avoid memory leaks.

  12. Finalize the SDK

    Call ppr_finalize_sdk to inform the SDK that it is no longer needed. This function releases the SDK's internally managed memory buffers. It must be called before exiting the program.

  1. Get a new context

  2. Enable recognition

  6. Cluster a gallery group

    The ppr_cluster_gallery_group function clusters templates within a gallery group to create an inter-gallery subject list. The resulting inter-gallery subject list indicates which templates from which galleries belong to the same subject.

  7. Free allocated memory

    Any gallery groups that were created or read from disk must be freed using ppr_free_gallery_group. Inter-gallery subject lists must be freed using ppr_free_inter_gallery_subject_list.

5. Example Applications

The following application is included to demonstrate usage of the clustering portion of the FTR-SDK and to provide an easy way to evaluate the SDK. A build script is provided to build all example applications. The applications can be passed a -help flag to get usage information.

clustering-cluster_gallery

This application reads a gallery from disk and clusters the gallery using the specified aggressiveness to create a subject list. A directory structure is created where each directory corresponds to a subject in the subject list, and each subject directory contains thumbnail images extracted from the templates that make up the subject. The input gallery file is updated to contain the new subject list. The application follows the Single-Gallery Clustering framework.
