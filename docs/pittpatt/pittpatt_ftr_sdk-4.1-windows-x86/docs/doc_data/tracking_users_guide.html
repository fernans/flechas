1. Definitions and Terminology

Face Tracking

Face tracking extends face detection to video sequences. Any individual who appears in a video for any length of time generates a face track - that is, a sequence of face instances across time. The goal of face tracking is to aggregate single-frame detection results into a collection of face tracks.

2. Introductory Topics

Enabling and Configuring Tracking

If tracking will be used, it must be enabled by calling ppr_enable_tracking before initializing the context. Tracking should not be enabled if it will not be used because it may marginally increase memory usage. After tracking is enabled, its context parameters can be configured by calling the functions listed in Initialize and Configure Functions. Finally, the context can be initialized by calling ppr_initialize_context.

Back to top.

Results

Detection returns a list of faces that have been found, along with a variety of meta-data on those faces. Tracking aggregates detected faces into face tracks from frame to frame. Data is reported by the tracker in two distinct ways: current tracks and completed tracks. The choice of which is best depends heavily on the application needs.

Completed Tracks

Completed track data is the final, and best, estimate of the full track data and is returned to the user after the track has been eliminated from possible future changes. Tracks are only reported if, at some point in their lifetime, they have met a variety of criteria. The one disadvantage of using completed track data is that the tracks are only reported after they have come to completion. For applications that do not require immediate results as each frame is processed, the completed track data is the most appropriate.

The primary data structure used for completed track results is ppr_completed_track_list_type. Completed track results can be obtained by calling ppr_get_completed_tracks.

Back to top.

Current Tracks

Current track data is the best immediate estimate of the tracked faces in the most recently submitted frame. One of the disadvantages of using current track data is that it is more susceptible to false alarms. This is because it is fairly common for tracks to start but never reach the required threshold for acceptance. Therefore, some tracks that appear (as low confidence) in this data will be rejected at a later time and will never make it to the completed track data. This can be partially remedied by ignoring the lowest confidence tracks in the current frame results. Current track data is useful when results are needed immediately after each frame is processed.

The primary data structure used for current track results is ppr_tracked_object_list_type. Current track results can be obtained by calling ppr_get_current_frame_objects.

Since a track and its constituent faces are updated every frame, the current track data is rarely the same as the eventual completed track data.

3. Advanced Topics

Visual Instances

Visual instances are cropped images containing the highest quality faces over the duration of a track. Larger faces are preferred over smaller faces, and high confidence faces are preferred over low confidence faces.

Visual instances are only available for completed tracks. The number of visual instances to store per track can be specified with the ppr_set_num_visual_instances function.

Back to top.

Tracking Cutoff

The trade-off between false alarms and misses is controlled by the tracking cutoff. A lower cutoff is more permissive, and therefore will result in a greater number of false alarms, but fewer misses. A higher cutoff is more restrictive, and therefore will result in fewer false alarms, but a greater number of misses. The cutoff value must be an integer between PPR_TRACKING_CUTOFF_MIN and PPR_TRACKING_CUTOFF_MAX. A cutoff of zero is standard and, on average, will result in the lowest overall error rate (sum of missed tracks and false alarm tracks).

Back to top.

Visual Attention

Visual attention is an algorithm implemented for tracking that can provide substantial speed improvements with little to no loss in accuracy. This is accomplished by searching only regions of sufficient interest from frame to frame. The algorithm respects custom search regions set with ppr_set_search_region by ignoring areas outside of the specified search region. Speed improvements are most pronounced in highly static scenes. The visual attention algorithm uses a key-framing approach to minimize errors. Every fifteenth frame is processed fully and every intermediate frame is compared with this key-frame to determine regions of interest.

In the extreme case of a completely static scene, the detector only processes 1 in 15 frames. The actual execution speed up is likely to vary between 1x and 15x depending on the scene content. In most cases, the impact on accuracy is minimal.

If tracking is enabled, the visual attention algorithm can be enabled by calling ppr_enable_visual_attention.

Shot Boundary Detection

A shot boundary is defined as a break of continuity in a camera shot. The shot boundary algorithm determines when a shot boundary has occurred and relays this information to the tracker. The tracker finalizes active tracks when it encounters a shot boundary. This explicit finalization of active tracks keeps tracks from being falsely merged across shot boundaries. The additional execution time needed for shot boundary detection is negligible.

If tracking is enabled, shot boundary detection can be enabled by calling ppr_enable_shot_boundary_detection.

Call ppr_set_shot_boundary_threshold to set a threshold that controls the sensitivity of shot boundary detection. The shot boundary threshold is a floating point number (greater than or equal to zero) that controls the sensitivity of the shot boundary algorithm. The threshold was normalized such that a threshold of 0.0 results in approximately 1 false alarm every 10,000 frames, and a threshold of 1.0 results in approximately 1 false alarm every 20,000 frames on an internal data set. The disadvantage of higher thresholds is that shot boundaries are more likely to be missed.

Back to top.

Detect and Track Calls

The ppr_detect_and_track_objects function can be used to do detection and tracking in one function call. Alternatively, detection and tracking can be broken into two steps by calling ppr_detect_objects followed by ppr_track_objects. Making independent calls to detection and tracking allows the user to thread detection at the frame level, with different threads processing different frames simultaneously. If this threading technique is used, it is important that objects are submitted to the tracking function in the proper frame order. The ppr_detect_and_track_objects function uses threading at a low level, but maximum throughput can be achieved by threading at the frame level.

4. Tracking Framework

Frameworks for using the tracking portion of the FTR-SDK are described below. The frameworks provide an introduction to the order in which functions should be called, with links to each function's detailed description.

Tracking Using Completed Results

This framework should be used when tracking results are not needed immediately after a frame is processed. Waiting for a track to complete before getting results from the tracker is the most accurate method and should be used when possible. If results are needed after each frame is processed because immediate action needs to be taken (for example, controlling a pan/tilt/zoom camera to track a person of interest), see Tracking Using Current Results.

  1. Get a new context

    Call ppr_get_context to get a new context with the default parameters. The returned context should be stored for submission to future function calls.

  2. Enable tracking

    Tracking must be enabled in the context before initialization since tracking functions will be used. Call ppr_enable_tracking to allow tracking functions to be used in the context.

  3. Configure the context

    Certain parameters cannot be configured after the context is initialized. Therefore, unless the default values are desired, the parameters must be configured before the initialization step. The function references indicate which parameters must be set before initialization.

  4. Initialize the context

    After configuring the context, ppr_initialize_context must be called before the context can be used.

  5. Submit a frame to the tracker

    Call ppr_detect_and_track_objects to submit a video frame to the tracker. Alternatively, detection and tracking can be performed in two separate calls using ppr_detect_objects followed by ppr_track_objects.

  6. Extract completed face tracks

    Extract completed face tracks through the present time with ppr_get_completed_tracks.

  7. Free allocated memory

    After processing (or storing) the application's required track data, release memory allocated for the completed track data structure with ppr_free_completed_track_list.

  8. Repeat for all frames

    Repeat steps 5 through 7 until the last frame in the video sequence has been processed.

  9. Force completion of remaining tracks

    After the last frame in the sequence has been processed, force completion of all remaining active tracks with ppr_finalize_current_tracks.

  10. Extract remaining face tracks

    Call ppr_get_completed_tracks one last time to extract any remaining face tracks.

  11. Free allocated memory

    Memory allocated for the track list data structure must be freed by calling ppr_free_completed_track_list.

  12. Release the context

    Call ppr_release_context to inform the SDK that the previously allocated context is no longer required. Each context must be released to avoid memory leaks.

  13. Finalize the SDK

    Call ppr_finalize_sdk to inform the SDK that it is no longer needed. This function releases the SDK's internally managed memory buffers. It must be called before exiting the program.

Note

Because the memory requirements for maintaining each stored track is relatively small, it is not necessary to perform steps 6 and 7 after every frame (once every 100,000 frames should be sufficient, though applications more sensitive to memory footprint may choose to do so more frequently). If performing off-line processing on a small video, steps 6 and 7 may not be necessary at all, and all completed tracks can be extracted after the entire video sequence has completed.

Tracking Using Current Results

This framework should be used when tracking results need to be acted upon frame-by-frame, as a video sequence is being processed. For this case, the framework outlined in Tracking Using Completed Results is not suitable since completed track results are only available after completion of face tracks. Because the tracking results after each frame are not as accurate as the completed track results, only use this framework when the application requires results to be processed before a track comes to completion.

  1. Get a new context

    Call ppr_get_context to get a new context with the default parameters. The returned context should be stored for submission to future function calls.

  2. Enable tracking

    Tracking must be enabled in the context before initialization since tracking functions will be used. Call ppr_enable_tracking to allow tracking functions to be used in the context.

  3. Configure the context

    Certain parameters cannot be configured after the context is initialized. Therefore, unless the default values are desired, the parameters must be configured before the initialization step. The function references indicate which parameters must be set before initialization.

  4. Initialize the context

    After configuring the context, ppr_initialize_context must be called before the context can be used.

  5. Submit a frame to the tracker

    Call ppr_detect_and_track_objects to submit a video frame to the tracker. Alternatively, detection and tracking can be performed in two separate calls using ppr_detect_objects followed by ppr_track_objects.

  6. Extract best estimate of active tracks

    Extract the best estimate of active faces in the current frame with ppr_get_current_frame_objects.

    This returns data pertaining to the faces in the current frame, but does not return data about entire tracks. Entire track data is not available until a track has completed. As with the previous scenario, call ppr_get_completed_tracks to get completed track data.

  7. Free allocated memory

    After acting on the current results, release memory for the tracked object list data structure with ppr_free_tracked_object_list.

    Note

    Memory associated with completed tracks must still be freed by the calling application, whether the completed track results are relevant or not for that application. Suppose that for this scenario, one does not care about preserving the data associated with completed tracks. Then, the calling application should periodically invoke ppr_discard_unreturned_completed_tracks. Alternatively, to preserve completed tracks (e.g., save to disk), the calling application can follow the same procedure as for Tracking Using Completed Results.

  8. Repeat for all images

    Repeat steps 5 through 7 until the last image in the sequence has been processed.

  9. Release the tracker's internally allocated memory

    Call ppr_discard_unreturned_completed_tracks one last time to free memory for any tracks remaining inside of the tracker.

  10. Release the context

    Call ppr_release_context to inform the SDK that the previously allocated context is no longer required. Each context must be released to avoid memory leaks.

  11. Finalize the SDK

    Call ppr_finalize_sdk to inform the SDK that it is no longer needed. This function releases the SDK's internally managed memory buffers. It must be called before exiting the program.

5. Example Applications

The following applications are included to demonstrate usage of the tracking portion of the FTR-SDK and to provide an easy way to evaluate the SDK. A build script is provided to build all example applications. The applications can be passed a -help flag to get usage information.

tracking-completed

This application uses the tracker to process a video sequence where results are extracted after tracks have come to completion. It follows the Tracking Using Completed Results framework.

tracking-current

This application demonstrates how to acquire frame-by-frame data from the tracker such that the results are extracted after every frame. It follows the Tracking Using Current Results framework.

tracking-threaded

This application demonstrates using frame-level threading for a tracking scenario. Instead of using the SDK's internal threading, threading is performed manually at the image level using POSIX Threads (pthreads). Since Windows does not ship with the pthreads library, this example program is not built by default for Windows users.
