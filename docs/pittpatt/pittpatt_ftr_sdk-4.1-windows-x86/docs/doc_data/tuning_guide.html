There are a number of parameters to consider when using the FTR-SDK. Some of the parameters affect speed, accuracy, and/or memory usage. Depending on application requirements, some may choose to achieve the best accuracy regardless of how much processing time is used. Others may be able to sacrifice some accuracy to decrease execution time. Some systems may have plenty of memory while others may have strict memory usage requirements. Because all applications are different, parameters are provided to allow the FTR-SDK to be tuned to an application's specific requirements.

1. Detection Precision

The detector has an option that allows the user to choose between coarse precision and fine precision. When using coarse precision, face detection uses fewer individual detectors, each spanning a larger range of angles than the fine precision detectors. This means that when using coarse precision the pose estimation is less precise than when using fine precision. In addition to less precise pose estimation, coarse detection also has the disadvantage of only working with the frontal landmark detector. Fine precision must be enabled for any other landmark detector types because they use the multi-pose landmark detector. Not only is the multi-pose landmark detector able to provide landmarks for non-frontal faces, it is also capable of providing more landmarks than the frontal landmark detector, which only detects the eyes and nose base.

One advantage of using coarse precision is that specific individual detectors can be specified. For example, if only frontal faces are desired, the detector can be told to only look for frontal faces. Individual detectors cannot be specified when using fine precision.

Because coarse precision uses less individual detectors than fine precision, face detection uses less processing cycles when using coarse precision. This is especially true if only a subset of the individual coarse detectors are activated. Using coarse precision also decreases memory usage and initialization time because fewer individual detectors need to be loaded into memory.

If an application does not need accurate pose estimation and only needs basic frontal landmarks, using coarse precision can decrease memory usage and execution time. But if accurate pose estimation is needed or the application needs multi-pose landmarks, then fine precision must be used. The detection precision can be specified using ppr_set_detection_precision. If coarse precision is being used, individual detectors can be specified using ppr_set_coarse_detector_types.

See Detection Precision for more information.

Coarse Precision Fine Precision
Faster detection Better pose estimation
Decreased memory usage Supports all landmark detectors
Faster initialization  
Individual detectors can be specified

2. Landmark Detection

Enabling landmark detection has two disadvantages. First, it increases memory usage because the individual landmark detectors must be loaded into memory. Second, searching for landmarks adds to the number of execution cycles. This is especially important when using automatic landmarks because all faces are searched for landmarks during detection. If only a subset of the detected faces need to be searched for landmarks, manual landmark detection can be used to mitigate the speed penalty.

The frontal landmark detector uses fewer execution cycles compared to the multi-pose landmark detector. Because the dual landmark detectors run the frontal detector followed by the multi-pose detector, the execution time varies depending on which detector finds landmarks.

Regardless of whether an application needs to know landmark locations, frontal landmarks are required for recognition. For applications that use recognition, there is no choice but to enable landmark detection.

Landmark detection should only be enabled if necessary. Use ppr_set_landmark_detector_type to specify the landmark detector to use, if any.

See Landmarks for more information.

Table 8.2. Landmark Detection Trade-Offs

Disabled Enabled
No cycles spent detecting landmarks User has option of searching for landmarks
Decreased memory usage Recognition can be used
Faster initialization

3. Search Pruning

Search pruning provides a way to greatly improve execution speed by limiting the number of scales and detectors that are needed to search an image. When a search pruning aggressiveness of two or higher is used, small faces may be missed as searching is discontinued after a high-confidence large face is found.

Search pruning requires single-threaded detection calls. Multi-threaded recognition calls may, and should, still be used. Use ppr_set_pruning_aggressiveness to specify the search pruning aggressiveness to use.

See Search Pruning for more information.

Table 8.3. Search Pruning Trade-Offs

Disabled Enabled
Exhaustively searches the image at all scales Much faster detection
Internal multi-threading may be used

4. Number of Threads

Most functions within the FTR-SDK are threaded internally. For processors with multiple cores or systems with multiple processors, using threading allows the SDK functions to take full advantage of the available processing power. Unless threading is handled elsewhere in the application, setting the number of threads to the total number of processing cores in the system provides better performance. Setting the number of threads to less than the number of processing cores prevents the SDK functions from taking advantage of the full processing power of the system. Setting the number of threads to more than the number of processing cores degrades performance because of unnecessary threading overhead.

For the best performance, threading of the detection functions should be performed outside of the SDK. This allows the use of search pruning which will result in the fastest execution times. Also, single-threaded detection calls are more memory-efficient than multi-threaded detection calls.

Set the number of threads to the number of processing cores unless alternative threading schemes will be used. Use ppr_set_num_detection_threads to indicate how many threads should be used by the detection functions and ppr_set_num_recognition_threads to indicate how many threads should be used by the recognition functions.

See Multi-Threaded Detection and Multi-Threaded Recognition for more information.

Single-Threaded Multi-Threaded
User has cores available for their own threading schemes SDK functions are automatically threaded internally
Search pruning may be used* SDK functions can take advantage of all of the processing power
Memory-efficient detection calls*  

*Only affected by number of detection threads, not number of recognition threads

5. Visual Attention

Visual attention can be used to decrease tracking execution time. When visual attention is enabled, only the parts of the image that change from frame-to-frame are searched. The decrease in execution time is most apparent when the scene is relatively static. There may be a minor accuracy penalty when using visual attention.

Use visual attention unless tracking accuracy seems to be adversely affected by it. Use ppr_enable_visual_attention to enable visual attention.

See Visual Attention for more information.

Table 8.5. Visual Attention Trade-Offs

Disabled Enabled
Accuracy not affected Decreased execution time, especially when scene is static

6. Visual Instances

Visual instances are images of a tracked face taken from different points during the track sequence. Do not set the number of visual instances greater than 0 unless they are truly necessary because there is a minor speed penalty associated with selecting visual instances as well as a slight increase in memory usage. The desired number of visual instances can be set using ppr_set_num_visual_instances.

See Visual Instances for more information.

Table 8.6. Visual Instances Trade-Offs

No Visual Instances One or More Visual Instances
No speed penalty Automatically selected images of tracked faces are available
Decreased memory usage

7. Minimum Size

Increasing the minimum face size can provide large speed improvements and great reductions in memory usage. The disadvantage of increasing the minimum size is that the smallest faces will not be detected.

For the best computational performance, set the minimum size as high as possible without missing required faces.

A face with a size less than 4 is unlikely to get accurate results from the recognizer. For applications that are strictly for recognition, setting the minimum size less than 4 is wasteful in terms of both memory and execution cycles.

Please read the section titled Face Sizes to determine how to choose the minimum size. Use ppr_set_min_size and/or ppr_set_adaptive_min_size to set the minimum face size.

Table 8.7. Minimum Size Trade-Offs

Low Minimum Size High Minimum Size
Smaller faces can be detected Much faster detection
  Much less memory usage

8. Maximum Size

Decreasing the maximum face size can provide speed improvements and reductions in memory usage. The disadvantage of decreasing the maximum size is that the largest faces will not be detected.

For the best computational performance, set the maximum size as low as possible without missing required faces.

Please read the section titled Face Sizes to determine how to choose the maximum size. Use ppr_set_max_size and/or ppr_set_adaptive_max_size to set the maximum face size.

Table 8.8. Maximum Size Trade-Offs

Low Maximum Size High Maximum Size

9. Search Regions

For applications that do not require the entire image to be searched, a search region can be specified. Since less of the image needs to be processed, the detector's execution time will be decreased, but faces outside of the search region will not be detected.

If it is known that there are places in the image where faces will not appear, set a search region using ppr_set_search_region.

See Image Search Regions for more information.

Table 8.9. Search Regions Trade-Offs

No Search Region Search Region Specified
Faces will be detected anywhere in the image Faster detection since only part of image is searched

10. Frontal Yaw Constraint

The frontal yaw constraint indicates what range of yaw angles is acceptable to consider a face to be frontal. Since templates can only be extracted for frontal faces, using the restrictive frontal yaw constraint reduces the number of cases where templates can be extracted. However, using the permissive setting can decrease overall recognition accuracy. The decrease in accuracy is due to the fact that as the difference in yaw angle between two faces increases, the ability of the recognizer to successfully match the two faces decreases. An application's overall execution time and memory usage may also increase when using the permissive setting because more templates will be generated and more matching will occur. Set the frontal yaw constraint using ppr_set_frontal_yaw_constraint.

Table 8.10. Frontal Yaw Constraint Trade-Offs

Restrictive Permissive
Better overall recognition accuracy Templates can be generated for more faces
Potentially lower overall execution time  
Potentially lower memory usage

12. Template Extraction

There are two different types of templates - single templates and double templates. Single templates are faster and use less memory while double templates are more accurate but use twice the memory and take twice as long to compare. The type of template extraction can be set with ppr_set_template_extraction_type.

See Template Extraction for more information.

Table 8.12. Template Extraction Trade-Offs

Single Double
Faster comparisons More accurate comparisons
Less memory usage

13. Multi-Gallery Clustering

Clustering requires comparing every template in a gallery to every other template in the gallery, creating a squared dependence between the number of templates in the gallery and the number of comparisons that must be performed. As the gallery size increases, the number of required comparisons grows quickly.

Multi-gallery clustering addresses this issue by using a two-stage clustering approach that greatly reduces the number of comparisons that must be performed. This greatly reduces the time required to do clustering at the expense of potentially less accurate clustering. It also reduces the amount of memory used because fewer comparison results must be stored.

See Multi-Gallery Clustering for more information.

Table 8.13. Multi-Gallery Trade-Offs

Single-Gallery Multi-Gallery
More accurate clustering Faster clustering
  Less memory usage

14. Representative Templates

When using multi-gallery clustering, the number of representative templates indicates how many templates from each stage one subject will be used to represent that subject in stage two. A large number of representative templates provides better accuracy at the expense of greater execution time and more memory usage. The number of representative templates can be set using ppr_set_num_representative_templates_per_subject.

See Representative Templates for more information.

Table 8.14. Representative Templates Trade-Offs

Low Number High Number
Faster clustering More accurate clustering
Less memory usage

15. Straggler Cutoff

When using multi-gallery clustering, the straggler cutoff controls which stage one subjects are represented at stage two. If the number of templates in a stage one subject is less than or equal to the straggler cutoff, that subject is not represented in stage two. A lower cutoff provides better accuracy at the expense of greater execution time and more memory usage. The straggler cutoff can be set by calling ppr_set_straggler_cutoff.

See Stragglers for more information.

Table 8.15. Straggler Trade-Offs

Low Cutoff High Cutoff
More accurate clustering Faster clustering
  Less memory usage

16. Disk Gallery Groups

When using multi-gallery clustering, the user has the option of using a disk gallery group. A disk gallery group stores the internal galleries on disk and only loads them when needed. This saves memory because only one gallery needs to be stored in memory at a time. However, it increases execution time because of the disk I/O that is needed.

See Disk Gallery Groups for more information.

Table 8.16. Disk Gallery Group Trade-Offs

Regular Gallery Group Disk Gallery Group
Faster clustering Less memory usage

Back to top.

17. Image Size

The amount of memory needed by the detector increases greatly as image size increases. Execution time also increases since a larger area must be searched. Although there is often no way around this, keep this in mind when writing applications. The detector is able to work on low-resolution images, so using downsized images may decrease detection time with little loss in accuracy.
